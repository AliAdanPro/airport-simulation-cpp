                        1. EXECUTIVE SUMMARY
================================================================================

This document provides a comprehensive theoretical and practical analysis of
the Smart Airport Operations Management System, a complex simulation that
demonstrates operating systems concepts including:

- Multi-threaded programming using POSIX threads (pthread)
- Mutex and read-write lock synchronization primitives
- Scheduling algorithms (HMFQ-PPRA)
- Memory/page replacement algorithms (AWSC-PPC)
- Resource allocation and deadlock prevention
- Real-time event processing

The system simulates a Tier-1 international airport with:
- 3 runways capable of handling aircraft from light jets to A380
- 40 gates (international, domestic, cargo, private)
- 7 types of ground resources (fuel trucks, baggage carts, etc.)
- Complete passenger and baggage processing pipelines
- Dynamic weather and crisis management
- Financial tracking and budget constraints

4.2 LIFECYCLE MANAGEMENT
─────────────────────────

INITIALIZATION SEQUENCE (initialize() method):
1. Create core components (DataManager, Scheduler, MemoryManager)
2. Create operational components with dependencies
3. Wire up inter-component dependencies (e.g., FlightManager needs RunwayManager)
4. Call initialize() on each component

START SEQUENCE (start() method):
1. Set running = true
2. Start Scheduler thread
3. Start MemoryManager thread
4. Record start time
5. Generate initial scheduled flights
6. Create and start simulation thread

STOP SEQUENCE (stop() method):
1. Set running = false
2. Join simulation thread
3. Stop Scheduler and MemoryManager threads

4.3 UPDATE LOOP
─────────────────

The main simulation loop (runSimulation()) runs in a dedicated thread:

LOOP CYCLE (runs at ~60 Hz):
1. Check if paused - if so, sleep 100ms and continue
2. Calculate real time elapsed since last iteration
3. Apply speed multiplier to get simulation time elapsed
4. Advance simulation time
5. Call update functions:
   - updateFlights(): Process flight state machine
   - updateGroundServices(): Advance ground service tasks
   - updatePassengers(): Process passenger pipeline
   - updateCrew(): Handle fatigue and breaks
   - updateCrises(): Update weather and emergency states
6. Every 60 simulation seconds:
   - updateStatistics(): Collect performance metrics
   - Simulate random events (crises, equipment failures)
   - Generate additional flights during rush hours
7. Sleep 16ms to maintain ~60 updates/second

FLIGHT STATE MACHINE (updateFlights):
The updateFlights() method processes active flights through their state machine:

SCHEDULED → [BUG: This transition is missing!]
APPROACHING → processArrival() → Request runway for landing
LANDING → [handled by runway timeout]
LANDED → Find and assign gate → TAXIING_IN
TAXIING_IN → After 5 min taxi time → AT_GATE, start turnaround
AT_GATE → When turnaround complete → PUSHBACK
PUSHBACK → processDeparture() → Request runway for takeoff → DEPARTING
DEPARTING → After 2 min takeoff → Release runway/gate → DEPARTED

5.2 RUNWAY MANAGER
───────────────────

File: aircraft.cpp (lines 15-276)

Manages runway allocation with wake turbulence separation:

LANDING REQUEST (requestLanding):
1. Find suitable runway (available, can handle category)
2. Check wake turbulence separation from last landing
3. Calculate required separation time based on categories
4. If runway available now, assign and mark OCCUPIED_LANDING
5. Set busyUntil = currentTime + 120 seconds (2 min landing)
6. Track last landing category for wake separation

TAKEOFF REQUEST (requestTakeoff):
1. Find available runway capable of handling aircraft
2. Assign and mark OCCUPIED_TAKEOFF
3. Set busyUntil = currentTime + 90 seconds (1.5 min takeoff)

WAKE TURBULENCE SEPARATION:
Uses Config::WAKE_SEPARATION matrix:
- SUPER behind SUPER: 180s
- SUPER behind HEAVY: 240s
- SUPER behind MEDIUM: 300s
- SUPER behind LIGHT: 360s
- LIGHT behind anything: 60s
- etc.

WIND HANDLING:
- handleWindChange(): Select optimal runway based on wind direction
- Close runways with crosswind component > 35 knots
- calculateCrosswindComponent using trigonometry

5.4 TAXIWAY NETWORK
────────────────────

File: aircraft.cpp (lines 541-913)

Graph-based taxiway network with A* pathfinding:

NETWORK STRUCTURE:
- Runway nodes: Entry/exit points for each runway
- Spine nodes: Main taxiway (ALPHA 0-9)
- Gate nodes: Individual gates

PATHFINDING (findPath):
Uses A* algorithm:
1. Initialize g-scores, f-scores, came-from
2. Add start node to priority queue
3. Process nodes by lowest f-score
4. For each neighbor not blocked:
   - Calculate tentative g-score
   - Update if better path found
   - Add to open set
5. Reconstruct path from came-from

GRIDLOCK DETECTION (detectGridlock):
- Check for occupied nodes where all neighbors blocked
- Gridlock if 3+ aircraft cannot move

PUSHBACK COORDINATION:
- requestPushback(): Check if pushback area clear
- Reserve taxiway node for pushback operation
- completePushback(): Release gate node

================================================================================
                    10. HMFQ-PPRA SCHEDULING ALGORITHM
================================================================================

Hybrid Multi-Level Feedback Queue with Predictive Priority Round-Robin and 
Aging (HMFQ-PPRA) is an 8-layer scheduling algorithm designed to handle 
complex airport operations efficiently.

10.1 LAYER 1: MULTI-LEVEL FEEDBACK QUEUE
─────────────────────────────────────────

FIVE PRIORITY QUEUES:

Queue 0 (EMERGENCY): Priority 0-10
- Quantum: Unlimited (run to completion)
- For: Fuel emergency, medical evacuation, critical system failures
- Never demoted

Queue 1 (CRITICAL): Priority 11-30
- Quantum: 200 time units
- For: Emergency landings, severely delayed flights (>2 hours)
- Demote to Queue 2 after 2 quantum expirations

Queue 2 (HIGH): Priority 31-50
- Quantum: 150 time units
- For: International long-haul, delayed flights (30-120 min), VIP
- Demote to Queue 3 after 3 quantum expirations

Queue 3 (NORMAL): Priority 51-75
- Quantum: 100 time units
- For: On-time domestic flights, cargo, regular operations
- Demote to Queue 4 after 4 quantum expirations

Queue 4 (LOW): Priority 76-100
- Quantum: 50 time units
- For: Private jets, non-critical ground operations, maintenance
- Cannot be demoted further

IMPLEMENTATION (scheduler.cpp):
- 5 deque<Operation*> queues with individual pthread mutexes
- determineInitialQueue(): Map priority to queue level
- demoteOperation(): Move to next lower queue, reset expiration count
- promoteOperation(): Move to specified higher queue

10.2 LAYER 2: PREDICTIVE IMPACT SCORE (PIS)
────────────────────────────────────────────

PIS quantifies the potential impact of delaying an operation:

FORMULA:
PIS = α × Delay_Propagation + β × Connection_Risk + γ × Resource_Utilization 
    + δ × Weather_Risk + ε × Fuel_Criticality

where α + β + γ + δ + ε = 1.0

WEIGHTS (from config.h):
- α (PIS_ALPHA) = 0.25: Delay propagation
- β (PIS_BETA) = 0.20: Connection risk
- γ (PIS_GAMMA) = 0.20: Resource utilization
- δ (PIS_DELTA) = 0.15: Weather risk
- ε (PIS_EPSILON) = 0.20: Fuel criticality

FACTOR CALCULATIONS:
- Delay_Propagation = Affected_Flights / Total_Flights
- Connection_Risk = Passengers_At_Risk / Total_Connecting_Passengers
- Resource_Utilization = Blocked_Resources / Total_Resources
- Weather_Risk = (Severity × Time_Affected) / Total_Resources (capped at 1.0)
- Fuel_Criticality = 0.8 for emergencies, 0 otherwise

USAGE:
Higher PIS → Lower priority number → Higher actual priority
Priority adjustment = PIS × 10 (subtracted from base priority)

10.3 LAYER 3: EXPONENTIAL AGING
────────────────────────────────

Prevents starvation using exponential aging:

FORMULA:
Age_Increment = Base_Age_Rate × e^(Wait_Time / Time_Constant)
Priority_Boost = Current_Priority - (Age_Increment × Age_Weight)

TIME CONSTANTS (per queue):
- Queue 4: 120 seconds (2 minutes) - fastest aging
- Queue 3: 180 seconds (3 minutes)
- Queue 2: 300 seconds (5 minutes)
- Queue 1: 480 seconds (8 minutes)
- Queue 0: 10000 seconds (effectively no aging)

IMPLEMENTATION:
- agingLoop(): Separate thread running runAging() every 1 second
- applyAging(): For each operation in queues 1-4:
  * Calculate wait time
  * Calculate exponential age increment
  * Reduce priority number (increase actual priority)

10.4 LAYER 4: DYNAMIC QUANTUM ADJUSTMENT
─────────────────────────────────────────

Adjusts quantum based on system load and operation type:

FORMULA:
Actual_Quantum = Base_Quantum × Load_Factor × Operation_Factor

LOAD FACTOR:
Load_Factor = 1 - (Active_Operations / Max_Operations)²
Range: [0.4, 1.0]

OPERATION FACTOR:
- Simple operations (taxiing): 0.7
- Medium operations (loading): 1.0
- Complex operations (full turnaround): 1.3

IMPLEMENTATION (calculateActualQuantum):
- Emergency queue: Unlimited (returns 999999)
- Get base quantum from queueQuantums array
- Calculate load factor from queue sizes
- Apply operation-specific factor
- Minimum: 10 time units

10.5 LAYER 5: PRIORITY INHERITANCE
───────────────────────────────────

Prevents priority inversion when high-priority blocked by low-priority:

MECHANISM:
1. High-priority operation blocked waiting for resource
2. Low-priority operation holding the resource
3. Temporarily boost low-priority to high-priority level
4. Track inheritance chain
5. Upon resource release, restore original priority

IMPLEMENTATION (applyPriorityInheritance):
- Check if blocker priority > blocked priority
- Save original priority
- Set blocker priority = blocked priority
- Create PriorityInheritanceChain record

IMPLEMENTATION (restorePriority):

- Restore originalPriority
- Remove from inheritanceChains map

10.6 LAYER 6: COST-BENEFIT PREEMPTION
──────────────────────────────────────

Decision-based preemption using cost-benefit analysis:

PREEMPTION BENEFIT:
Benefit = Urgency × Delay_Cost
- Urgency = 1 - (priority / 100)
- Delay_Cost = wait_time × 0.1

PREEMPTION COST:
Cost = Progress_Lost × 0.5 + Context_Switch_Cost + Resource_Config_Cost 
     + Downstream_Impact × 10
- Context_Switch_Cost = 5.0
- Resource_Config_Cost = 2.0
- Downstream_Impact = PIS

DECISION (shouldPreempt):
if (Benefit > 1.5 × Cost) → Preempt

EXECUTION (executePreemption):
1. Save state of preempted operation
2. Set isPreempted = true, increment preemptionCount
3. Give compensation (reduce quantum expiration count)
4. Add preempted operation to front of queue (fairness)

10.7 LAYER 7: STARVATION PREVENTION
────────────────────────────────────

MAX WAIT THRESHOLDS:
- Queue 4: 15 minutes (900 seconds)

- Queue 2: 30 minutes (1800 seconds)

MECHANISM (checkStarvation):
For operations in queues 2, 3, 4:
1. Calculate wait time
2. If wait > threshold AND not already guaranteed:
   - Set hasGuaranteedService = true
   - Promote to CRITICAL queue (Queue 1)
   - Log starvation prevention

After completion, reset guaranteed service flag.

================================================================================
                    11. AWSC-PPC PAGE REPLACEMENT ALGORITHM
================================================================================

Advanced Working Set Clock with Predictive Prefetching and Adaptive 
Compression (AWSC-PPC) is an 8-component page replacement algorithm.

11.1 COMPONENT 1: ENHANCED WORKING SET TRACKING
────────────────────────────────────────────────

Dynamic per-process working set window:

FORMULA:
Δ_actual = Δ_base × Phase_Multiplier × Load_Multiplier × Fault_Rate_Multiplier

BASE WINDOW: 15 time units

PHASE MULTIPLIERS:
- Initialization: 1.5 (more pages during startup)
- Computation: 1.0 (stable working set)
- I/O: 0.7 (less memory actively used)
- Termination: 0.5 (reducing footprint)

LOAD MULTIPLIERS:
- Light (<40% memory): 1.3
- Medium (40-70%): 1.0
- Heavy (70-90%): 0.8
- Critical (>90%): 0.6

FAULT RATE MULTIPLIERS:
- <5%: 0.9 (can reduce working set)
- 5-15%: 1.0 (maintain current)
- >15%: 1.2 (increase working set)

11.2 COMPONENT 2: MULTI-PASS CLOCK
───────────────────────────────────

Each page frame maintains metadata (PageFrame struct):
- pageId, processId
- Reference Bit (R), Modified Bit (M)
- Access Frequency (F): 16-bit counter with decay
- Last Access Time (T)
- Access Pattern: Sequential/Random/Strided
- Working Set Member (W): Boolean
- Prefetch Candidate (P): Boolean
- Compression Ratio
- Lock Bit (L): Pinned pages
- Prediction Score: Future access probability

THREE-PASS SELECTION:

PASS 1: Working Set Protection
- Skip if working set age ≤ Δ AND W = true
- Skip if L = true (locked)
- If R = 1: Clear R, increment F, update pattern, continue
- If R = 0: Add to candidate list

PASS 2: Scoring and Selection
Victim_Score = (Freq_Component × W_freq) + (Rec_Component × W_rec) 
             + (Pattern_Component × W_pat) + (Pred_Component × W_pred)
             - (Dirty_Penalty × M) - (Compression_Benefit × Compression_Ratio)

Components:
- Frequency: 1 / (F + 1) — higher F → lower score → less likely evicted
- Recency: (Current_Time - T) / Avg_Lifetime — older → higher score
- Pattern: Sequential=0.5, Random=1.0, Strided=0.7
- Prediction: 1 - Prediction_Score — high future access → less eviction
- Dirty Penalty: 2.0 if modified
- Compression Benefit: -0.8 if ratio > 0.5

Weights: W_freq=0.3, W_rec=0.3, W_pat=0.2, W_pred=0.2

Select page with HIGHEST Victim_Score.

PASS 3: Forced Replacement (if no candidate)
1. Find oldest clean page outside working set
2. Find least frequently used modified page outside working set
3. Select random page from lowest priority process
4. (Last resort) Evict from current process

11.3 COMPONENT 3: PREDICTIVE PREFETCHING
─────────────────────────────────────────

PATTERN DETECTION:
- Sequential: Pages accessed as i, i+1, i+2... → Prefetch next 3-5 pages
- Strided: Pages accessed as i, i+k, i+2k... → Prefetch i+4k, i+5k
- Loop: Same pages repeatedly → Lock in memory, mark as hot

PREFETCH TRIGGER:
if (Pattern_Detected AND Memory_Available > 20%):
    Prefetch_Count = min(5, Available_Frames / 4)
    Prefetch next pages in detected pattern
    Mark as Prefetch_Candidate

11.4 COMPONENT 4: ADAPTIVE COMPRESSION
───────────────────────────────────────

CANDIDATE SELECTION:
if (F < Threshold_Freq AND (Current_Time - T) > Compression_Age):
    Attempt_Compression(Page)

COMPRESSION:
if (Compressed_Size < 0.6 × Original_Size):
    Store compressed version
    Free original frame
    Mark as compressed
    Update Compression_Ratio

DECOMPRESSION:
On page fault for compressed page:
    Decompress to available frame
    Update access statistics
    Add decompression time to latency

11.5 COMPONENTS 5-8: ADDITIONAL FEATURES
─────────────────────────────────────────

COMPONENT 5: FREQUENCY DECAY
Every 1000 time units:
    For all pages: F = F × 0.9
    (Gives more weight to recent access patterns)

COMPONENT 6: PROCESS PRIORITY INTEGRATION
Victim_Score multiplier:
- High priority process: ×2.0 (less likely evicted)
- Medium priority: ×1.0
- Low priority: ×0.5 (more likely evicted)

COMPONENT 7: THRASHING DETECTION AND PREVENTION
Fault_Rate = Page_Faults_Last_Minute / Total_Memory_Accesses

if (Fault_Rate > 0.25):
    Enter Thrashing_Prevention_Mode:
    - Suspend lowest priority processes
    - Increase working set windows by 50%
    - Disable prefetching
    - Compress more aggressively
    - Reduce active processes

COMPONENT 8: MACHINE LEARNING PREDICTION (Simplified)
Markov Chain for page access prediction:
- Transition_Matrix[Page_i][Page_j] = Probability of Page_j after Page_i
- On access: Increment Transition_Matrix[Previous][Current], normalize
- Prediction: Next = argmax(Transition_Matrix[Current][j])
- If probability > 0.6: Assign high Prediction_Score, protect from eviction

                    16. BUG ANALYSIS: FLIGHTS STUCK AT ZERO
================================================================================

SYMPTOM:
When running the simulation, all metrics show 0:
- Active Flights: 0
- Flights Processed: 0
- Gate Utilization: 0%
- All resources show as available

ROOT CAUSE ANALYSIS:

1. Flight Creation (generateScheduledFlights, line 490-509):
   - Creates 20 flights with status = SCHEDULED
   - Scheduled arrival times: 60 to 7200 seconds from start

2. Active Flight Query (getAllActiveFlights, lines 1055-1067):
   ```cpp
   if (pair.second.status != FlightStatus::DEPARTED &&
       pair.second.status != FlightStatus::CANCELLED &&
       pair.second.status != FlightStatus::SCHEDULED) {  // <-- PROBLEM!
       result.push_back(&pair.second);
   }
   ```
   This EXCLUDES flights with SCHEDULED status!

3. Flight Update (updateFlights, line 354):
   ```cpp
   std::vector<Flight*> activeFlights = flightManager->getAllActiveFlights();
   ```
   Only processes "active" flights, which excludes SCHEDULED.

4. MISSING TRANSITION:
   There is NO code that transitions flights from SCHEDULED to APPROACHING
   when their scheduledArrival time is reached!

CONSEQUENCE:
- Flights are created as SCHEDULED
- They never become APPROACHING
- getAllActiveFlights() never returns them
- updateFlights() never processes them
- They remain SCHEDULED forever
- All metrics stay at 0

THE FIX:
Add code at the beginning of updateFlights() to check all flights:
- For each flight with status == SCHEDULED
- If simulationTime >= flight.scheduledArrival
- Transition to status = APPROACHING
